# torch-tbccl 0.2.0 validation (draft)

```{warning}
**This is not a certification.** torch-tbccl 0.2.0 is the first release; it was promoted from release candidate 0.2.0rc1 without runtime changes. This page summarizes validation of the development tree against TBCCL C ABI 1 and wire protocol 4, plus the checks run on the published release-candidate wheels. A condensed list of exercised configurations is on the [validated configurations](../project/validated-configurations.md) page.
```

## Configuration under test

| | |
|---|---|
| PyTorch / CPython | 2.13.0 / 3.13 |
| TBCCL | C ABI 1, wire protocol 4 (development tree) |
| Linux | x86-64, NVIDIA RTX 3070 Ti Laptop GPU, CUDA 13 |
| macOS | Apple silicon, MPS |
| Physical link | direct Thunderbolt 4 cable between the two hosts |

## Test suites (recorded results, historical)

| Suite | Result |
|---|---|
| Linux (CPU, CUDA, DDP, lifecycle, failure, mixed traffic, capability matrix; MPS tests skip) | 229 passed, 59 skipped |
| macOS (everything, including MPS and clean-install tests; CUDA tests skip) | 201 passed, 87 skipped |

## Supported-surface contract

The capability matrix (every operation x dtype x payload shape x world size and device mode, driven through the public `torch.distributed` API on loopback) is compared with the documented surface by `tests/test_capability_matrix.py`; the MPS matrix (280 records at world sizes 1 and 2) had no wrong, failed or hung cell and no deviation from the documented surface.

## Packaging

Linux CPU and CUDA wheels and the macOS wheel were built, inspected (no embedded machine paths; the macOS wheel links only system Metal, Foundation and Objective-C runtime libraries and no libtbccl) and installed into clean virtual environments where a real collective ran.

## Mixed traffic and DDP

Collectives and point-to-point on one group at world sizes 2 to 4 on CPU, CUDA and MPS in same, opposite and mirrored order; DDP with a concurrent application P2P thread (CPU world sizes 2 and 3, CUDA plus CPU, MPS plus CPU with a CPU side channel).

## Failure and lifecycle

Peer exit, abort, destroy with pending work and interpreter shutdown with an un-waited asynchronous operation (repeated runs) are bounded and report `torch-tbccl:` errors; peer-failure tests are loopback only.

## Physical Thunderbolt 4 runs

CPU, CUDA to MPS point-to-point and collectives, and DDP (10 steps, repeated cycles) with a concurrent P2P thread, in both orientations, with the PCIe AER counters read before and after: no data mismatch and zero AER errors throughout; devices preserved. No failure was injected on the physical link.

## Known limits

Listed in [Supported operations](../reference/supported-operations.md) and the [MPS guide](../guides/mps.md): `SUM` only; two-rank gather; float16 and bfloat16 reduction at world size 2 only; no reduce, scatter, reduce_scatter, all_to_all or all_gather_into_tensor; no FSDP; DDP not at world size 1; MPS limited to one submitting thread; no fault recovery.

## Release-candidate wheel checks

The published 0.2.0rc1 wheels (Linux x86-64 with the CUDA 13 build of PyTorch, macOS arm64) were installed into clean virtual environments from the release artifacts, byte-identical to the published files, and exercised on a Linux CUDA host and a Mac joined by Thunderbolt 4: point-to-point (one-way, reverse and simultaneous), mixed asynchronous all_reduce with point-to-point in flight, all_reduce (float32 at 4 KiB, 1 MiB and 16 MiB, float16 and bfloat16 at 1 MiB), broadcast from both roots, all_gather and barrier between a CUDA rank and an MPS rank, in both rank orientations, with no mismatch and devices preserved; and nine failure and lifecycle cases with a Linux CUDA survivor. All passed with unchanged link health. DDP over the physical link was validated on the development tree (above) and was not repeated with the release-candidate wheels.

## Not yet done for a release

The final 0.2.0 release itself: no `v0.2.0` tag, wheels or numbered documentation exist yet.

## Release 0.2.0 public-wheel gate

The 0.2.0 wheels were built by CI from `v0.2.0` (commit `0c40c7139d3adca9f07b08aa167406eb8093ee5a`) against TBCCL 0.6.0; checksums and attestations verify. They were installed with `--no-deps` into clean virtual environments (PyTorch 2.13.0, CPython 3.13) on the Linux CUDA host and the Mac, and exercised over the physical Thunderbolt 4 link with `tools/physical_ops.py` (CUDA rank 0 with a CPU peer: point-to-point and all_reduce, exact values, 4 KiB to 16 MiB) and `tools/hetero_ops.py` (CUDA rank 0 with an MPS peer, and MPS rank 0 with a CUDA peer: point-to-point both ways, simultaneous, all_reduce, broadcast, all_gather; every payload bit-compared). All runs exited 0 on both hosts, and the kernel log showed no AER or link events. The MPS peer-failure test (`allreduce_peer_exit_during`) accepts the failure at submission or at wait; it failed 3 of 3 before the change and passed 12 of 12 after it on the Mac.
