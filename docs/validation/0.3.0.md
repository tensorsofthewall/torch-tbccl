# torch-tbccl 0.3.0 validation

```{warning}
**This is not a certification.** torch-tbccl 0.3.0 is a minor release of 0.2.1 whose wheels bundle TBCCL 0.7.0 (C ABI 1, wire protocol 4). No adapter source changed since 0.2.1; this page records the validation of the development tree and of the CI-built artifacts of release candidate 0.3.0rc1, from which 0.3.0 was promoted without a code change.
```

## What changed

The adapter source (`csrc/`, `torch_tbccl/`) is unchanged since 0.2.1. The differences are the TBCCL that the wheels bundle (0.7.0 instead of 0.6.1) and the documentation of the opt-in AllReduce pipeline.

## Tests on a build against the TBCCL 0.7.0 development tree

| Check | Result |
|---|---|
| Linux (CUDA PyTorch 2.13.0) adapter test suite | 393 passed |
| macOS (PyTorch 2.13) adapter test suite | 360 passed |
| Loaded native library | rebuilt in an isolated directory against the 0.7.0 tree; the loaded binary was checked to contain the new AllReduce setting (published 0.2.1 wheels do not) |
| Collective correctness, CPU/CPU and CUDA/MPS over Thunderbolt 4, both orientations | AllGather and AllReduce, pipeline off and on, passed |
| Default behaviour | unchanged; DDP step time with the setting unset was within about 1% of the published 0.2.1 wheel |

## Performance review

Interleaved fresh process pairs, both orientations, a DDP model of about 33.6 MB with 25 MB buckets. AllGather latency fell by 25% to 66% in the sampled sizes. With `TBCCL_ALLREDUCE_PIPELINE_BYTES=131072` the DDP step fell by 33% to 53% (CPU/CPU and CUDA/MPS). One apparent outlier in a 4 KiB CUDA/MPS AllGather did not reproduce with more repetitions. PCIe AER reporting was unavailable on the Linux host, so nothing is claimed about PCIe errors.

## Release-candidate artifacts

The CI-built wheels of 0.3.0rc1 (Linux x86-64 with the CUDA 13 build of PyTorch, macOS arm64) were installed into clean environments on both hosts, with their checksums, SBOMs and attestations verified, and the loaded `libtbccl` checked to be the 0.7.0 runtime. The wheel test suites ran in CI on the exact commit.

| Check | Result |
|---|---|
| Collectives (`all_reduce`, `all_gather`, `broadcast`, `barrier`, point-to-point), CPU/CPU and CUDA/MPS, both orientations | correct; `all_gather` faster, default `all_reduce` within noise of 0.2.1, `all_reduce` with `TBCCL_ALLREDUCE_PIPELINE_BYTES=131072` 19% to 66% faster |
| DDP, Model M, CPU/CPU and CUDA/MPS, against 0.2.1 | default step time within 1.5%; with the pipeline setting 34% to 55% faster; all results correct |

An intermittent delay of about 350 ms per launch for unpipelined 16 MiB CUDA/MPS collectives occurred with the 0.2.1 and 0.3.0rc1 wheels alike while the link showed elevated TCP retransmissions (no interface errors or drops); it did not occur with the pipeline setting. It is recorded as a known limitation of the link, not a change of this release.

The physical checks above used a single Linux CUDA / Apple Metal machine pair. PCIe AER reporting was unavailable on the Linux host (`pci=noaer`); no statement about PCIe errors is made.
